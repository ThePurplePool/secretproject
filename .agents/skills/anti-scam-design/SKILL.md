# Anti-Scam Uzbekistan — Product Design Skill

## 1. Product Identity

Anti-Scam Uzbekistan is NOT a generic SaaS platform, analytics dashboard, LMS, cybersecurity portal, or AI showcase.

It is an immersive behavioral cybersecurity training platform.

The primary product experience is:

REALISTIC SITUATION
→ TIME PRESSURE
→ USER DECISION
→ CONSEQUENCE
→ EXPLANATION
→ RETRY
→ SKILL DEVELOPMENT

The user should feel that they have entered a real-world situation rather than opened an educational website.

The interface must create contextual immersion.

---

# 2. Core Design Principle

## The UI should feel like a real situation, not like a website explaining a situation.

Bad:

A card saying:

"Suspicious Bank Message"

with:

[Read Message]
[Make Decision]

Good:

A realistic messenger interface containing a suspicious message, sender information, attachment, timestamp, typing indicator, notification state, and a visible countdown.

The user interacts with the situation itself.

---

# 3. Design Direction

Use a professional cybersecurity product aesthetic with strong editorial/product-design discipline.

The visual language should communicate:

* trust
* seriousness
* realism
* urgency
* clarity
* controlled tension
* human-centered cybersecurity

Avoid turning the product into a "hacker/cyberpunk" website.

The experience should feel closer to:

* a premium security product
* a realistic simulation
* a digital safety training environment
* an interactive decision system

than to:

* an AI startup landing page
* a crypto dashboard
* a generic SaaS admin panel
* a gaming website

---

# 4. STRICTLY AVOID

Do NOT use these patterns unless there is a strong contextual reason:

* generic SaaS dashboard
* hero section + three cards
* giant centered headline
* purple AI gradients
* blue/purple gradient backgrounds
* excessive glassmorphism
* floating glowing blobs
* excessive rounded cards
* "Welcome back"
* meaningless KPI cards
* decorative charts
* stock hacker imagery
* cyberpunk city imagery
* neon green terminal aesthetics
* random circuit-board graphics
* excessive shadows
* excessive animations
* every element inside a rounded rectangle
* identical card layouts everywhere
* generic AI-generated illustrations
* "AI-powered" visual clichés
* huge abstract gradient text
* unnecessary sidebars
* dashboard UI when the user is actually inside a simulation

Never add decorative elements simply because an empty area exists.

Whitespace is allowed.

---

# 5. Scenario-First Architecture

The scenario is the primary UI object.

Do NOT build:

Page
→ Header
→ Sidebar
→ Card
→ Scenario inside card

Prefer:

Application Shell
→ Scenario Environment
→ Contextual Controls
→ Decision Layer

Examples:

Telegram scenario:

Application shell
→ realistic messenger

SMS scenario:

Application shell
→ realistic mobile messaging interface

Email scenario:

Application shell
→ realistic inbox/message interface

Browser scenario:

Application shell
→ browser chrome + webpage

Bank scenario:

Application shell
→ banking interface

Phone scam:

Application shell
→ incoming call / conversation interface

---

# 6. Situational Interfaces

The platform must support multiple interface environments.

Required environments:

1. Messenger
2. SMS
3. Email
4. Browser
5. Banking application
6. Social network
7. Marketplace / delivery
8. Phone call
9. Government/service portal
10. Mobile application

Each environment must have its own visual grammar.

Do NOT render every scenario as a generic card.

---

# 7. Realism Rules

Interfaces should contain realistic contextual details:

* timestamps
* sender names
* avatars
* message status
* notification badges
* attachment names
* URL previews
* browser address bars
* email metadata
* transaction information
* phone numbers
* call duration
* application navigation
* contextual warnings

However:

DO NOT clone real companies or official interfaces 1:1.

Use fictionalized but familiar entities.

Examples:

"Bank Uzbekistan"

"UZ Delivery"

"Government Service"

"Job Center"

"Online Market"

The interface should feel familiar without impersonating a real organization.

---

# 8. Time Pressure

Time pressure is a core gameplay mechanic.

It is NOT merely a decorative stopwatch.

Example:

20 sec
→ calm

15 sec
→ subtle urgency

8 sec
→ stronger warning

3 sec
→ final pressure

The interface should visually communicate increasing urgency.

Use restrained motion.

Do not make the UI look like an arcade game.

The timer should be visually prominent but must not destroy usability.

---

# 9. Psychological Manipulation

Every scenario should communicate one or more manipulation mechanisms.

Examples:

* urgency
* authority
* fear
* reward
* scarcity
* impersonation
* social pressure
* curiosity
* financial opportunity
* emotional manipulation

The interface should subtly reinforce the psychological pressure.

Example:

Fake bank:

"Your account will be blocked in 10 minutes."

Fake police:

"Failure to respond may result in legal consequences."

Fake relative:

"Please help me urgently."

The design should make the pressure believable without becoming melodramatic.

---

# 10. Decision Interface

Decisions must feel like actions available to a real user.

Prefer:

[Open attachment]

[Check sender]

[Delete message]

[Report]

over:

[A]
[B]
[C]
[D]

The user should understand what each action means without relying on a quiz-like interface.

Actions may be:

* clicking a message
* opening an attachment
* visiting a URL
* entering information
* answering a call
* refusing a request
* reporting a message
* checking sender information
* closing a browser
* contacting an official channel

---

# 11. Consequence Visualization

When the user makes a dangerous decision, show consequences visually.

Do NOT simply display:

"Incorrect answer."

Instead show:

ACTION
↓
ATTACK
↓
CONSEQUENCE

Example:

Opened malicious attachment

↓

Malware execution

↓

Device compromise

↓

Potential access to personal data

↓

Potential financial loss

Use a simulated financial consequence where appropriate.

Example:

Initial balance:
10,000,000 UZS

Potential simulated loss:
−1,500,000 UZS

Remaining simulated balance:
8,500,000 UZS

Always label this as:

"Симулированный потенциальный ущерб"

Never imply that the platform caused an actual financial transaction.

---

# 12. Error State

An error state must teach.

Every dangerous decision should explain:

1. What the user did.
2. Why it was dangerous.
3. Which manipulation technique was used.
4. Which warning signs were present.
5. What should have been done.
6. What the real-world response should be.

Example structure:

⚠ Потенциально опасное действие

Вы открыли вложение.

Почему это опасно:
Файл может содержать вредоносный код.

Психологическая техника:
Срочность + impersonation.

Признаки:
• неожиданный файл
• давление по времени
• подозрительный отправитель

Правильное действие:
Проверить отправителя через официальный канал.

---

# 13. Retry

After an incorrect decision, provide:

ПОПРОБУЙТЕ ЕЩЁ РАЗ

But do not simply repeat the same question.

Use transfer learning.

Example:

Scenario 1:
Fake bank message

Scenario 2:
Fake government message

Scenario 3:
Fake delivery message

The manipulation mechanism may remain similar.

The user must recognize the pattern in a new context.

---

# 14. Progression

Three levels:

LEVEL 1
Anti-Scam Basic

Goal:
Recognize suspicious situations.

LEVEL 2
Anti-Scam Defender

Goal:
Protect yourself and others.

LEVEL 3
Anti-Scam Consultant

Goal:
Explain and analyze scam situations independently.

Progression should be visible but not gamified excessively.

Avoid:

XP explosions
loot boxes
fake achievements
arcade badges everywhere

Use a restrained professional certification system.

---

# 15. Consultant Mode

At Level 3 the user becomes a consultant.

Do not simply display:

"Congratulations! You are an expert."

Instead create an interactive assessment.

Example:

Another participant receives a suspicious message.

The user must explain:

* what is happening
* scam type
* manipulation technique
* warning signs
* correct action
* potential consequences

The system evaluates the explanation.

After successful completion:

Anti-Scam Consultant

Certificate
Digital Badge

Then:

"Теперь вы можете помочь защитить ещё 5 человек."

This is a social education mechanism.

It must NOT resemble MLM, referral marketing, or financial incentives.

---

# 16. Certificate Design

Certificates should look institutional and professional.

Avoid:

gaming certificates
neon badges
oversized decorative graphics
cheap gradients

Prefer:

* clean typography
* institutional hierarchy
* certificate number
* participant name
* achievement
* completion date
* verification mechanism
* QR code where appropriate

---

# 17. Fraud Reporting

Reporting should feel like a practical public-service feature.

Supported inputs:

* phone number
* Telegram/WhatsApp account
* URL
* screenshot
* message
* payment details
* description
* call information

Keep the form simple.

Do not turn reporting into a complicated CRM form.

After submission:

"Сообщение принято."

Then explain:

"Информация может использоваться для выявления связанных мошеннических схем."

Do not claim that a scammer was blocked, investigated, or punished unless the backend actually performs that operation.

---

# 18. Fraud Intelligence

Fraud Intelligence is primarily an operational/admin interface.

Entities may include:

Report
Phone
Account
URL
Domain
Payment Requisite
Message
Scenario
Scam Cluster

The admin interface may use tables, graphs and relationship visualizations.

This is one of the few places where a conventional dashboard is appropriate.

However:

Do not expose internal intelligence complexity to normal training users.

---

# 19. AI Voice Scam Simulator

The AI Voice module should feel like a phone call.

Do NOT create:

"AI Chatbot" card.

Instead create:

Incoming call

Caller identity

Call duration

Conversation state

Live transcription where appropriate

Actions:

Answer
Decline
Ask question
End call
Report

The caller can use:

* urgency
* authority
* fear
* impersonation
* reward
* emotional pressure

The interface should progressively communicate pressure.

After the call:

Duration
Decisions
Manipulation techniques
Critical moments
Outcome
Feedback

Never request real:

* passwords
* OTPs
* bank card numbers
* PINs
* banking credentials

---

# 20. Motion Design

Motion should have functional meaning.

Use animation for:

* timer progression
* message arrival
* notification
* state transition
* consequence
* warning
* success
* scenario progression

Avoid:

* constant floating animations
* decorative blobs
* excessive parallax
* excessive page transitions
* animation on every card

Animation should increase immersion, not advertise that the site was AI-generated.

---

# 21. Responsive Design

Mobile is a primary platform.

Design for:

1. mobile
2. tablet
3. desktop

Scenario interfaces must remain believable on small screens.

Do not simply shrink the desktop interface.

Adapt the interaction model.

Example:

Desktop:
browser chrome + webpage + decision panel

Mobile:
mobile browser + contextual action sheet

---

# 22. Accessibility

Maintain:

* readable contrast
* keyboard navigation
* visible focus
* semantic HTML
* accessible labels
* reduced-motion support
* readable typography
* non-color-only warnings

Do not sacrifice accessibility for realism.

---

# 23. Visual Hierarchy

Every screen must have:

1. Primary context
2. Primary action
3. Secondary actions
4. Status
5. Supporting information

The user's attention must be obvious.

Do not give equal visual weight to ten different elements.

---

# 24. Design System

Before implementing a large UI, establish:

* typography
* spacing scale
* color system
* semantic colors
* border radius
* elevation
* iconography
* motion principles
* component states

Use semantic colors:

success
warning
danger
info
neutral

Do not make the entire application red/black simply because it is cybersecurity.

---

# 25. Color Direction

Default direction:

Neutral, professional foundation.

Use strong colors primarily for:

* danger
* warning
* success
* important actions
* timer states

Avoid permanent neon colors.

Avoid purple AI gradients unless explicitly requested.

The visual hierarchy must survive in grayscale.

---

# 26. Typography

Typography should prioritize:

* readability
* hierarchy
* credibility
* compact information density where appropriate

Use no more than a small number of font families.

Do not use futuristic display fonts merely to make the product look "cyber".

---

Good:

---

# 28. Page Design Rules

Before creating any page, answer:

1. What is the user trying to accomplish?
2. What situation are they in?
3. What is the primary action?
4. What information is necessary?
5. What can be removed?
6. What should the user notice first?
7. What happens after the action?

If these questions cannot be answered, do not start implementation.

---

# 29. Anti-Generic AI Check

Before considering a UI complete, inspect it for these symptoms:

[ ] Does it look like a generic SaaS dashboard?

[ ] Does it contain unnecessary gradient backgrounds?

[ ] Does it use excessive rounded cards?

[ ] Does it look like an AI startup landing page?

[ ] Could the same UI be used for a CRM, HR platform, or project management tool?

[ ] Are scenario interfaces represented as generic cards?

[ ] Is there decorative cyberpunk imagery?

[ ] Are there meaningless charts?

[ ] Are animations decorative rather than functional?

[ ] Does the interface communicate the actual situation?

If the answer to any of the first eight questions is YES, redesign the relevant area.

The Anti-Scam product must have a recognizable product identity.

---

# 30. Scenario Quality Check

Every scenario implementation must answer:

* What is the user's situation?
* Who is communicating with them?
* Why does the situation feel believable?
* What psychological pressure exists?
* What information is visible?
* What decision must be made?
* What happens after the decision?
* What is the simulated consequence?
* What does the user learn?
* Can the skill transfer to another scenario?

---

# 31. Implementation Rule

Do not redesign the architecture simply to achieve visual quality.

Preserve:

* React
* TypeScript
* existing routing
* scenario engine
* API contracts
* persistence
* security controls

Improve the presentation layer and UX architecture without unnecessarily rewriting functioning business logic.

---

# 32. Before Writing UI Code

First inspect:

* existing components
* existing design tokens
* routes
* scenario schema
* state management
* API contracts
* existing CSS/Tailwind configuration

Reuse existing infrastructure where appropriate.

Do not introduce a new UI library solely because it is visually fashionable.

---

# 33. When Creating New Screens

Follow this sequence:

1. Identify the user goal.
2. Identify the context.
3. Select the appropriate situational interface.
4. Define the information hierarchy.
5. Define primary and secondary actions.
6. Define success/error/loading states.
7. Define responsive behavior.
8. Define motion.
9. Implement.
10. Visually review.
11. Remove generic AI patterns.
12. Test interaction states.

---

# 34. Final Design Principle

The platform should not tell the user:

"You are learning about phishing."

It should make the user think:

"Shit. Is this message real?"

That moment of uncertainty is the core of the product.

The platform teaches cybersecurity by making users experience the decision pressure that scammers exploit.

Every visual and interaction decision should reinforce this principle.
